# Carda validation plan — protocol draft, not results

Date: 30 September 2026. Applies to every F01–F20 criterion in [`requirements-matrix.md`](requirements-matrix.md). Eleven open hospital sensor recordings have been checked for **exploratory offline** F12 development; see [`dataset-register.md`](dataset-register.md) and E-20260929-016/020/021/022. A metadata-ID-grouped split reserves validation and held-out records, but the evaluation protocol and patient independence have not been signed off. Internal Kotlin `rr-research-0.2` has synthetic software checks for both baseline and pulse-amplitude modulation; it does not turn the hospital-sensor baseline into phone-camera evidence or enable user RR. A CardioGAN research checkpoint has been restored/converted and its gated Android CPU runtime compared on **synthetic** signals E-20260929-031/033–035; this is not model confidence, phone-camera, R-peak or physiological validation. No Carda phone-domain dataset, reference instrument, participant, approved protocol, physical device test or validated metric result has been confirmed. This draft must be reviewed, resourced and frozen **before** a final evaluation set is examined. Source targets in [`final-feature-scope.md`](../final-feature-scope.md) are pilot planning targets, not clinical sample-size claims.

## Evidence levels and release rule

1. **Synthetic** fixtures prove deterministic code, edge cases and safety gates only.
2. **Emulator** proves UI, lifecycle, permission and persistence paths possible without real fingertip optics.
3. **Physical device** proves camera/torch/cadence/lifecycle behavior on the listed hardware and conditions.
4. **Reference comparison** tests metric agreement with a named, synchronized instrument under stated conditions. Report accepted error **with** acceptance/yield and all rejections.
5. **Usability and expert review** test task performance, comprehension and wording; neither validates sensor physiology by itself.

For each study: record consent/protocol ID, operator, build SHA/version, pipeline/model/threshold versions, hardware and reference versions, timing alignment, environment/activity, number of distinct people and sessions, exclusions/rejections, accepted errors, confidence intervals or uncertainty, limitations and aggregate-safe evidence location. Store raw participant files only in an approved access-controlled research location, never Git, app analytics or production backend. Partition development/calibration and final evaluation by **participant**, with devices and session grouping described. Pre-register acceptance thresholds for error, yield/retry, latency and relevant subgroup performance; do not tune after looking at final outcomes. A changed algorithm, threshold, camera config, model or relevant UI flow invalidates affected evidence until regression or evaluation is rerun.

**Safety stop:** no numerical physiological result, trend point, export or ECG Insight after failed SQI. A metric-specific gate can withhold one metric while preserving independently valid results. Treat a correct withheld result as safety evidence, not completion of that feature. Do not induce hypoxia, abnormal rhythm or BP changes for a demo without an approved protocol and qualified supervision.

## Metric-specific protocols

| Metric / owner | Software correctness and gate | Physiological study and analysis | Completion boundary |
| --- | --- | --- | --- |
| **Capture/SQI** F02–F04, `core:camera`/`core:ppg` | Fixture windows: normal, dark, overexposed, clipped, weak/unstable coverage, motion/noise, irregular cadence, too short, error/exception and ambiguous irregular signal. Ensure close-once for `ImageProxy`, bounded queue, stop torch on every exit, no stale result. | On each phone, controlled placement/light/motion/retry, supported and restricted profile, repeated measurements. Compare a documented ungated baseline with gated output using accepted-result error, coverage, false accepts/rejects, retry and latency. Do not call low periodicity a diagnosis. | Fixture pass ≠ camera compatibility. Need real-phone matrix with reasons and an empirically justified threshold version. |
| **HR** F05 | Deterministic timestamp/peak/count fixtures including boundary BPM, missed/extra beat, resampling and failed SQI; result absent on invalid window. | Paired rest sessions, ECG preferred, measured simultaneously and aligned in time. Pulse-ox display only a labelled exploratory comparator. Compute MAE, signed bias, limits of agreement, distribution, per-phone/person errors, failed sessions, acceptance rate and retry/time; use participant-aware uncertainty. | Only assert performance for tested devices, population, posture and conditions; SQI score is not accuracy percentage. |
| **PRV RMSSD/SDNN** F09 | Timestamped beat fixtures and artefact handling; sufficient intervals/duration/cadence per metric; independent HR/PRV availability. | Synchronized camera PPG pulse events and ECG R peaks, same valid period. Compare interval-level error and RMSSD/SDNN bias/agreement by person/device/condition, accepted/rejected proportion, arrhythmic or uncertain windows separately. | Call values PPG-derived PRV; ECG HRV equivalence requires evidence. BPM-only reference cannot validate this. |
| **ECG Insight** F10 | Model-loading/hash/I-O/sampling and inference tests with a licensed fixture; CPU fallback, shape/SQI/confidence rejection, model absence and graceful HR independence. Confidence must be evaluated separately from SQI. | Subject-separated paired PPG–ECG dataset for method development, then synchronized **Carda phone camera PPG–ECG** set. Report waveform error/correlation, R-peak timing, interval error, calibration and failure cases by device/condition; compare domain shift. Expert reviews any rhythm-category proposal. | A plausible-looking line or evaluation on hospital PPG alone does not validate user-facing phone ECG. No five diagnostic-style rhythm labels until evidence and review. |
| **SpO₂** F11 | Specify optical-channel/calibration algorithm and reject saturation, exposure variation, unsupported device and out-of-range input; unit tests must not use HR or SQI as SpO₂ truth. | Pair with a calibrated reference oximeter for a **comparator-agreement pilot**, recording device, skin/lighting and observed saturation range. A pulse oximeter reading is not arterial SaO₂ ground truth or clinical accuracy evidence; a clinical-performance claim would need an appropriately reviewed co-oximetry protocol and population/range coverage. Report bias/absolute error/limits, range-stratified error, calibration/test separation, drift and yield. Healthy normal-range samples cannot validate <95% bands. | No user number or Normal/Critical label outside proven range. If needed range cannot be safely sampled, feature remains unvalidated, not deleted. |
| **Respiratory rate** F12 | Internal `rr-research-0.2` has provisional 58–70 s, ≥20 fps, bounded-sample, cadence, artifact and modulation gates. The input is one snapshot checked against a report from the same configured global SQI evaluator. Synthetic baseline and amplitude-only pulse modulation have separate candidates; changing-rate and absent-modulation fixtures are withheld. Before product use, compare both methods and freeze thresholds against a development set without inspecting reserved final records. | Align phone PPG with belt/capnography; manual counted breaths only limited pilot. Analyze breaths/min absolute/signed error, rate/condition subgroup, time lag, accepted/rejected windows and rejection causes. Include baseline modulation **and** amplitude/frequency modulation, motion and device/exposure variation so a synthetic pass does not hide a missing mechanism. | Distinguish breaths/min from cardiac R–R ms; source sensor dataset is not phone-domain proof. The internal candidate appears only as a transient debug research note, not a production result/history/export metric, and needs physiological validity plus reviewed usage conditions before output. |
| **SBP/DBP** F13 | Feasibility review of identifiability and calibration input first; tests for calibration expiry, subject/device mismatch, invalid inputs and uncertainty/withheld output. | Compare against validated cuff with repeated, synchronized readings, variation beyond one rest baseline, calibration/evaluation separated by sessions and persons where applicable; report SBP and DBP error, bias, limits, drift, yield by device and pressure range. | No numeric estimate from single-camera PPG absent supported method and validation. Report scientific gap and resources if unsolved. |
| **Interpretation/risk** F14 | Each versioned rule has sourced rationale, exact required metrics, quality gate, missing-data behavior and Indonesian copy test. Test no alert from unavailable or stale values. | Expert review of clinical implications and false reassurance/alarm; user comprehension of uncertainty and action wording, especially older participants. Audit proposed four source categories individually. | A rule table or expert opinion alone is not diagnostic validity; do not expose unsupported triage/disease claims. |

Candidate public datasets, including PhysioNet BIDMC where license and annotations are checked, may support offline methods. [`dataset-register.md`](dataset-register.md) records acquisition, license, sensors, checksum and the reserved metadata-ID-grouped split. The 11-record **Python sensor-PPG development baseline** has a worst recording MAE of 7.87 breaths/min and no respiratory SQI; it cannot support F12 output. The separate Kotlin RR research gate E-047 has synthetic correctness evidence only and no measured agreement or yield. Before validation/held-out use, verify patient independence, freeze an algorithm/gate and numeric criteria with a study lead. Sensor PPG and camera PPG are different domains. Training data may not be embedded in the APK; release models need license and model card.

**F11/F13 method audit, not Carda evidence:** published [smartphone RGB SpO₂ work](https://www.nature.com/articles/s41746-022-00665-y) and [OptiBP camera pulse-wave work](https://www.nature.com/articles/s41598-020-74955-4) show that optical settings, device/domain and algorithm ownership matter; neither supplies a validated Carda estimator. The cited OptiBP article identifies an oBPM patent application, so its result cannot be treated as permission to reproduce its algorithm. The [F3Mamba smartphone dataset page](https://github.com/Health-HCI-Group/F3Mamba) requests a data-release agreement and institutional email; no Carda access or redistribution right is assumed. [FDA draft pulse-ox guidance](https://www.fda.gov/media/184896/download) distinguishes noninvasive oximeter readings from arterial co-oximetry and discusses skin-pigmentation/range evaluation; it is draft guidance, not a Carda approval. These sources define research questions and potential access paths only. No associated dataset was downloaded or used as a Carda validation set in this checkpoint.

## Freeze and reporting template

Before final data collection, create a versioned protocol per metric with: intended population/activity and exclusion criteria; reference instrument and calibration; target device matrix; sample and repeat plan; synchronized acquisition procedure; preprocessing/model version; specific primary/secondary statistics and numeric pass thresholds; handling of missing/rejected/failed sessions; subgroup analyses; privacy/consent; and stop rules. A study owner and reviewer sign the freeze date. No number is invented here for physiological error thresholds because no qualified protocol or reference resources are yet confirmed.

For every result report `n_people`, `n_attempts`, `n_accepted`, `n_rejected_by_reason`, metric error on accepted attempts, coverage, uncertainty, per-device findings and unresolved conditions. Publish only aggregate-safe summaries and link them through [`evidence-index.md`](evidence-index.md). Mark related evidence `requires-rerun` whenever the frozen pipeline, thresholds, model, acquisition or reviewed wording changes.
